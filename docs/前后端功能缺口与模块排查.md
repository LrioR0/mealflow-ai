# MealFlow 前后端功能缺口与模块排查

更新时间：2026-10-06

## 一、结论摘要

### 冰箱库存删除失败的原因

这次删除失败**不是因为系统是“纯前端”**。库存删除链路实际上已经具备完整后端接口：

```text
前端 deleteInventoryItem()
  → DELETE /api/v1/inventory/{item_id}
  → inventory_service.delete_item()
  → 数据库删除 InventoryItem
  → HTTP 204 No Content
```

真正的问题在于前端公共请求封装：

```text
apps/web/src/api/client.ts
```

原逻辑无论返回什么状态，都执行 `response.json()`。但删除接口返回 `204 No Content`，响应体为空，导致前端在后端已经删除成功后继续抛出 JSON 解析异常，后面的刷新逻辑也无法正常执行，因此用户看到的效果像是“删除失败”。

已修复：公共 API 客户端现在会对 `204` 和空响应直接返回，不再调用 JSON 解析。

## 三、已经修复的问题

### 3.1 库存删除 204 响应解析

文件：

```text
apps/web/src/api/client.ts
```

现在处理逻辑为：

1. 非 2xx 响应抛出错误；
2. `204 No Content` 直接返回；
3. 空响应直接返回；
4. 有响应体时再解析 JSON。

这会同时修复所有返回 `204` 的前端接口，不只影响库存删除。

### 3.2 库存删除后刷新

文件：

```text
apps/web/src/views/admin/InventoryView.vue
```

原本的删除流程已经正确：

```text
确认 → DELETE → 成功提示 → refresh()
```

问题是公共请求封装在 DELETE 成功后解析空响应失败，导致 `refresh()` 没有执行。修复请求封装后，此链路可以正常运行。

## 四、仍然缺少后端的功能

## 4.1 采购清单后端持久化

当前文件：

```text
apps/web/src/views/admin/ProcurementView.vue
apps/web/src/composables/procurement.ts
```

当前采购清单保存在：

```text
localStorage: mealflow_procurement_v1
```

问题：

- 换浏览器后数据消失；
- 换设备后无法同步；
- 无法和账号、家庭工作区绑定；
- 多人协作时无法共享；
- Agent 无法从后端读取真实采购状态；
- 无法记录采购历史、购买时间和实际价格。

建议后端新增：

```text
GET    /workspaces/{workspace_id}/procurement-items
POST   /workspaces/{workspace_id}/procurement-items
PATCH  /procurement-items/{item_id}
DELETE /procurement-items/{item_id}
POST   /procurement-items/{item_id}/complete
```

建议数据字段：

```text
id
workspace_id
ingredient_key / ingredient_name
quantity
unit
source: agent | manual
source_run_id
checked
checked_at
created_at
updated_at
```

## 4.2 下厨足迹后端持久化

当前 `CookingHistoryView.vue` 使用 localStorage：

```text
mealflow_cooking_history_v1
```

现有前端能力包括：

- 菜名；
- 图片；
- 做菜人；
- 下厨时间；
- 份量；
- 难度；
- 食材；
- 步骤；
- 评分；
- 下次改进建议；
- 用户评价。

后端目前没有对应模型、迁移和接口。建议新增：

```text
GET    /workspaces/{workspace_id}/cooking-records
POST   /workspaces/{workspace_id}/cooking-records
PATCH  /cooking-records/{record_id}
DELETE /cooking-records/{record_id}
POST   /cooking-records/{record_id}/reviews
```

图片还需要独立的上传或对象存储方案，不能长期依赖 base64 存在浏览器 localStorage 中。

## 4.3 Agent 修改家庭档案

目前 Agent 能读取成员限制并用于规划，但尚不能可靠执行：

```text
给 Liro 添加虾过敏
让妈妈加入本次用餐
把对象的例假设置到明天
取消我的感冒事件
```

要实现真正的对话修改，需要：

1. Agent 意图识别；
2. 成员、限制、事件的工具调用；
3. 高风险过敏修改的确认机制；
4. SSE mutation 事件；
5. 前端家庭档案和用餐人员面板刷新。

当前基础 REST 接口已经存在，但对话 Agent 尚未接入这些写操作。

## 4.4 本次用餐人员作用域

前端已经发送：

```text
diners_user_ids
```

但后端 `ChatStreamRequest` 即使接收到该字段，当前规划上下文仍然会加载整个工作区的成员约束。结果是：

- 前端看起来选中了本次用餐人员；
- 实际规划仍可能把全家限制全部合并进去；
- 访客和未用餐成员的约束可能误影响方案。

后端需要在 `load_planning_context` 或聊天服务层增加 selected diner scope：

```text
selected member restrictions
selected member events
workspace-wide restrictions
```

并明确全家共享红线与本次成员限制的合并优先级。

## 4.5 餐后反馈和口味迭代

旧版 feedback 路由、schema 和 service 当前已删除。数据库虽然保留部分 Agent 状态结构，但没有完整的家庭餐后反馈闭环。

需要新增：

- 评分接口；
- 菜品标签反馈；
- 不喜欢原因；
- 反馈与成员绑定；
- 口味权重聚合；
- 下一次规划读取反馈；
- 前端即时反馈卡片。

## 4.6 图片识别冰箱库存

需求文档要求：

- 上传冰箱照片；
- 识别食材；
- 判断新鲜程度；
- 估算保质期；
- 用户确认后写入库存。

当前前后端均没有对应实现。至少需要：

```text
POST /workspaces/{workspace_id}/inventory/vision/recognize
```

返回：

```text
ingredient candidates
confidence
estimated freshness
suggested expires_on
```

前端必须提供确认步骤，不能直接把视觉模型结果写入库存。

## 4.7 真实认证和权限

当前路由守卫仍是演示模式：

```text
router.beforeEach() 直接放行
```

登录页也是占位页。后续需要：

- 登录接口；
- token/session；
- workspace 权限；
- 成员数据权限；
- Agent 操作权限；
- 采购与档案修改的审计记录。

## 4.8 自定义单位校验

前端已经支持填写：

```text
番茄 3 个
```

但后端 `inventory_service.py:107-110` 仍要求单位必须等于食材默认单位。例如番茄默认 `kg`，填写 `个` 会返回单位不匹配。

如果要正式支持自定义单位，需要后端选择一种方案：

1. 允许原样保存单位，不进行换算；
2. 建立单位换算表；
3. 区分采购单位和库存计量单位；
4. 允许每个库存项独立单位。

当前前端入口已经有了，但后端业务规则尚未完成。
