# MealFlow 食序：技术开发文档

> 版本：0.1（MVP 设计基线）  
> 状态：待实现。本文记录已确认的技术方案、接口边界与实施约定；除仓库中已经存在的项目文档外，文中描述的应用、接口和部署能力均尚未落地。

## 1. 目标与边界

MealFlow 是面向企业食堂的菜单规划、库存协同及员工反馈应用。产品采用“一套账号、多个工作区”的模型以兼容未来个人版；国庆 MVP 只启用企业食堂工作区。MVP 要完成「食堂站点与餐次 → 库存维护 → 批量菜单推荐 → 采购清单 → 菜单发布 → 员工反馈」的闭环。

系统以确定性规则保证事实正确性：库存、保质期、过敏原、饮食限制、营养估算和采购清单均由后端服务计算。LLM 只负责解析自然语言、选择已注册工具和把工具结果组织成易读说明，不能绕过硬约束或直接写入核心业务数据。

首版不包含真实注册、成员邀请、图像识别、供应商下单、医疗或疾病诊断、社交社区及复杂机器学习模型。营养值须标示为估算，不能作为医疗建议。

## 3. 架构与职责

### 3.1 技术栈

- Web：Vue 3、Vite、TypeScript、Pinia、Element Plus。
- API：Python 3.12+、FastAPI、Pydantic v2、SQLAlchemy 2.x、Alembic。
- 存储：MVP 使用 SQLite；部署或多人并发使用 PostgreSQL。
- Agent：LangGraph（编排）与 LangChain（工具适配）；模型供应商由环境变量选择。
- 测试：Pytest（后端与规则）、Vitest（前端单元测试）、Playwright（关键链路）。
- 交付：Docker Compose；CI 运行静态检查、测试和镜像构建。

### 3.2 分层

```text
Vue 页面 / Pinia 状态
          │ HTTPS / JSON
FastAPI Router ── Pydantic Schema
          │
Application Service ── Rule Engine ── Agent Tool Adapter
          │                  │                 │
SQLAlchemy Repository  Recipe/Inventory Data  LLM Provider
          │
SQLite / PostgreSQL
```

Router 只处理鉴权、参数校验和 HTTP 响应；Service 承载业务用例；Repository 负责持久化；Rule Engine 保持无副作用且可独立测试。Agent 通过同一组 Service/工具读取数据，写入操作必须先由前端确认后调用明确的写工具。

## 4. 核心数据模型

所有表使用 UUID 主键、`created_at` 和 `updated_at`（UTC）。数量使用 `Decimal`，禁止浮点数；金额以分为单位的整数存储。

| 实体 | 关键字段 | 关系/约束 |
| --- | --- | --- |
| site | workspace_id、name、service_capacity | 食堂站点；MVP 使用一个站点。 |
| meal_service | site_id、service_date、name、expected_diners、status | 餐次如午餐；`expected_diners > 0`。 |
| dietary_restriction | workspace_id、type、ingredient_key、severity | 用餐人群限制；过敏原为硬约束。 |
| kitchen_tool | workspace_id、tool_key | 厨具影响可做菜的筛选。 |
| ingredient | id、key、name、category、default_unit | `key` 全局唯一，作为匹配和替代基准。 |
| inventory_item | workspace_id、ingredient_id、quantity、unit、purchased_on、expires_on | `quantity >= 0`；过期品默认不参与可用库存。 |
| recipe | id、name、servings、duration_minutes、difficulty、image_source、tags | 图片及内容来源必须可追溯。 |
| recipe_ingredient | recipe_id、ingredient_id、quantity、unit、optional、substitutes | 配方食材明细。 |
| recipe_step | recipe_id、step_no、instruction、duration_minutes | `(recipe_id, step_no)` 唯一。 |
| meal_plan | workspace_id、start_date、days、status、constraints_snapshot | 保存生成时的约束快照以便解释。 |
| meal_plan_item | meal_plan_id、meal_date、meal_type、recipe_id、servings、score_breakdown | 同一餐位不重复菜谱。 |
| feedback | user_id、meal_plan_item_id、status、rating、leftover_level | `rating` 取 1–5；用于后续特征工程。 |
| interaction_event | workspace_id、user_id、event_type、recipe_id、context | 记录曝光、查看、评分等匿名化事件。 |

为兼容未来个人版，所有业务数据统一按 `workspace`（工作区）归属，并新增以下基础实体：

| 实体 | 关键字段 | 关系/约束 |
| --- | --- | --- |
| user | id、email、password_hash、display_name | 身份只存一次，不把用户类型固化在 user 表。 |
| workspace | id、name、kind、owner_id | MVP 固定 `organization`；保留 `personal` 供未来个人版。 |
| workspace_member | workspace_id、user_id、role、status | 唯一 `(workspace_id,user_id)`；角色为 `owner`、`manager`、`member`。 |

库存、成员偏好、菜单、反馈及事件表均保存 `workspace_id`，查询必须由当前工作区作用域过滤。不要在每张表增加 `is_enterprise`，也不要让“企业用户”成为不可变的 user 属性。

食材单位换算需维护独立的 `unit_conversion` 配置；无法安全换算的单位必须返回「需人工确认」，不能静默合并。

## 5. 规则引擎与菜单生成

### 5.1 推荐流程

1. 读取食堂站点、餐次、预计用餐人数、饮食限制、厨具和本次自然语言约束。
2. 读取未过期库存，计算距到期日不超过阈值（默认 3 天）的临期食材。
3. 从结构化菜谱库召回候选；过滤过敏原、明确限制、缺少必需厨具和超过餐次时间上限的菜谱。
4. 计算菜谱分数并按分数排序；按 `expected_diners / recipe.servings` 放大食材用量。
5. 基于选中菜单与库存计算缺口，按食材品类聚合采购清单。
6. 保存计划后，LLM 仅根据已返回的事实生成推荐理由与替代建议。

建议的可解释分数（初版权重可配置）：

```text
score = 0.40 * expiring_ingredient_coverage
      + 0.25 * preference_match
      + 0.20 * time_fit
      + 0.10 * budget_fit
      + 0.05 * feedback_affinity
      - repeat_penalty
```

任一硬约束不满足即淘汰，不能用高分抵消。返回结果须包含 `score_breakdown`、命中临期食材、被过滤原因及缺少食材，供界面与测试使用。

### 5.2 Agent 工具契约

首批工具为：`get_workspace_profile`、`get_meal_service_context`、`list_inventory`、`search_recipe_candidates`、`score_recipes`、`calculate_nutrition`、`build_procurement_list`、`save_meal_plan`、`publish_meal_plan`、`save_feedback`。

- 读取工具返回经 Pydantic 校验的 JSON，不返回 API Key、原始模型消息或不必要的个人信息。
- `save_meal_plan`、`publish_meal_plan` 与 `save_feedback` 是副作用工具，必须带工作区与角色作用域并进行权限校验。
- Agent 运行配置最大步骤数、超时和工具白名单；工具失败时停止写操作并返回可恢复的错误。
- UI 应展示「采用的约束、调用的工具、推荐依据」，但不暴露内部提示词和密钥。

## 6. REST API（v1 草案）

统一前缀 `/api/v1`。成功响应为业务对象或 `{ "items": [], "meta": {} }`；错误格式为 `{ "code": "...", "message": "...", "details": [] }`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / PUT | `/workspaces/{workspace_id}/profile` | 查询或更新食堂档案、用餐限制、厨具。 |
| GET / POST | `/workspaces/{workspace_id}/inventory` | 查询或新增库存项。 |
| PATCH / DELETE | `/inventory/{item_id}` | 修改数量/日期或删除库存项。 |
| GET | `/recipes`、`/recipes/{recipe_id}` | 菜谱检索和详情。 |
| POST | `/meal-plans/preview` | 按约束生成但不保存的菜单及解释数据。 |
| POST / GET | `/meal-plans`、`/meal-plans/{id}` | 保存并读取菜单计划。 |
| POST | `/meal-plans/{item_id}/feedback` | 记录烹饪反馈。 |
| POST | `/shopping-lists/preview` | 根据计划和库存生成缺货清单。 |
| POST | `/agent/chat` | 流式或非流式自然语言规划；仅调用白名单工具。 |
| GET / POST | `/sites` | 查询或维护食堂站点。 |
| GET / POST | `/meal-services` | 查询或维护餐次与预计人数。 |
| POST | `/meal-plans/{id}/publish` | 管理员发布菜单。 |

`POST /meal-plans/preview` 最少接收 `workspace_id`、`start_date`、`days`、`meal_types`、`time_limit_minutes` 和可选的 `budget_cents`、`preference_text`。返回值必须带 `constraints_applied`、`items`、`shopping_list` 和 `explanations`。写接口使用 `Idempotency-Key` 以避免网络重试产生重复计划或反馈。

## 7. 前端页面与状态

- 演示身份切换：在预置的管理员和员工身份间切换；真实登录留到国庆后。
- 食堂档案：站点、餐次、预计人数、用餐限制与厨房条件；保存前展示硬约束提示。
- 冰箱库存：按到期日排序，临期和过期状态显著区分，支持入库、消耗和编辑。
- 菜单规划：输入人数、日期、时长、偏好；先调用 preview，再由用户确认保存。
- 菜谱详情：封面、原料、缺口、步骤、总耗时、替代建议与来源。
- 采购清单：按品类归并，显示按人数放大后的所需量、现有量、缺少量及无法换算项。
- 员工反馈页：已用餐/未用餐、评分与剩余量；管理端查看聚合结果。

Pinia 只保存当前工作区、演示身份和短期 UI 状态；服务端数据以 API 为准。所有异步状态须有 loading、empty、error 和 retry 状态。

## 8. 配置、安全与隐私

提交 `.env.example`，实际 `.env` 不入库。最低配置为 `DATABASE_URL`、`LLM_PROVIDER`、`LLM_API_KEY`、`LLM_MODEL`、`CORS_ORIGINS`、`LOG_LEVEL`。生产环境还应设置认证密钥、速率限制和受信任代理配置。

- API Key 仅保留在后端环境变量，禁止出现在前端构建产物、日志、异常详情与测试快照中。
- 所有资源按 `workspace_id` 鉴权；不得仅凭对象 ID 读取或修改他人数据。每一个 Repository 查询都必须接收工作区作用域。
- 过敏原/忌口数据按敏感偏好处理，日志只记录必要的匿名标识。
- 校验日期、数量、单位、评分和文本长度；对 Agent、保存计划和反馈接口限流。
- 菜谱图片、营养资料和替代关系须记录来源、许可和采集日期。

## 9. 本地开发、测试与交付

实施后应提供以下标准命令（以实际包管理器为准）：

```text
docker compose up --build
cd apps/api && pytest
cd apps/web && npm run lint && npm run test && npm run build
```

测试最低覆盖：过敏原与饮食限制过滤、过期/临期计算、单位换算、按人数放大、库存缺口、分数排序、API 权限隔离和 Agent 工具失败回退。端到端测试至少验证「配置餐次与人数 → 录入库存 → 生成预览 → 保存/发布菜单 → 采购清单 → 员工反馈」。

CI 建议分为 `lint`、`test-api`、`test-web`、`e2e`（可选）、`build`；PR 合并前至少要求 lint、单元测试和构建通过。数据库演进使用 Alembic 迁移，禁止依赖应用启动时自动改表。

## 10. 实施顺序与验收

1. 建立后端/前端骨架、环境样例、数据库迁移与 30–50 道可追溯种子菜谱。
2. 交付食堂站点/餐次、库存 CRUD、临期规则和菜谱详情。
3. 交付硬约束过滤、按人数换算、评分、菜单预览/保存/发布及采购清单，并完成规则测试。
4. 接入 Agent，限制为解释和受控工具编排；完成工具调用审计展示。
5. 补齐反馈、Docker Compose、CI、演示脚本和发布说明。

MVP 验收以如下场景为准：总部食堂午餐预计 120 人，库存含鸡蛋、番茄、土豆、鸡胸肉和临期食材，并设置花生限制与清淡偏好；输入「明天午餐，优先消耗临期番茄，清淡」后，系统给出不违反限制的批量菜单、可解释原因、准确采购缺口；管理员能够发布菜单，员工能够提交反馈。
