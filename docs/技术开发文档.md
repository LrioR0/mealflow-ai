# MealFlow 食序：技术开发文档

> 版本：1.0（国庆后演示版技术基线）
> 状态：待实现。本文记录已确认的技术方案、接口边界与实施约定；除仓库中已经存在的项目文档外，文中描述的应用、接口和部署能力均尚未落地。

## 1. 目标与边界

MealFlow 是面向政府机关食堂的运营决策 Agent。产品采用“一套账号、多个工作区”的模型以兼容未来个人版；V1 只启用组织工作区。V1 在国庆期间用 3–4 天完成，国庆后演示「自然语言目标 → 工具编排 → 多方案比较 → What-if 重规划 → 管理员发布 → 公共 PC 自助终端匿名反馈 → 下一轮改进」的闭环。

系统以确定性规则保证事实正确性：库存、保质期、过敏原、饮食限制、营养估算和采购清单均由后端服务计算。LLM 只负责解析自然语言、选择已注册工具和把工具结果组织成易读说明，不能绕过硬约束或直接写入核心业务数据。

V1 按 Agent-first 原则实施：库存、采购、菜谱和 Kiosk 是 Agent 的感知、计算、执行和反馈工具，只做闭环所需的最小页面。项目完成度优先由多步骤工具编排、状态保持、重规划、解释、人工确认和降级评判，而不是由 CRUD 页面数量评判。

首版不包含真实注册、成员邀请、图像识别、供应商下单、医疗或疾病诊断、社交社区及复杂机器学习模型。营养值须标示为估算，不能作为医疗建议。

## 3. 架构与职责

### 3.1 技术栈

- Web：Vue 3、Vite、TypeScript、Pinia、Element Plus。
- API：Python 3.12+、FastAPI、Pydantic v2、SQLAlchemy 2.x、Alembic。
- 存储：MVP 使用 SQLite；部署或多人并发使用 PostgreSQL。
- Agent：LangGraph（编排）与 LangChain（工具适配）；模型经 `LLMProvider` 接入。V1 只使用云端 API，千问为主、DeepSeek 备用、智谱为验证后候选，不包含本地模型部署。
- 测试：Pytest（后端与规则）、Vitest（前端单元测试）、Playwright（关键链路）。
- 交付：Docker Compose；CI 运行静态检查、测试和镜像构建。

### 3.2 分层

```text
Vue 页面 / Pinia 状态
          │ HTTPS / JSON
FastAPI Router ── Pydantic Schema
          │
Application Service ── Rule Engine ── Agent Tool Adapter
          │                  │                 │
SQLAlchemy Repository  Recipe/Inventory Data  LLM Provider
          │
SQLite / PostgreSQL
```

Router 只处理鉴权、参数校验和 HTTP 响应；Service 承载业务用例；Repository 负责持久化；Rule Engine 保持无副作用且可独立测试。Agent 通过同一组 Service/工具读取数据，写入操作必须先由前端确认后调用明确的写工具。

## 4. 核心数据模型

所有表使用 UUID 主键、`created_at` 和 `updated_at`（UTC）。数量使用 `Decimal`，禁止浮点数；金额以分为单位的整数存储。

| 实体 | 关键字段 | 关系/约束 |
| --- | --- | --- |
| site | workspace_id、name、service_capacity | 食堂站点；MVP 使用一个站点。 |
| meal_service | site_id、service_date、name、expected_diners、status | 餐次如午餐；`expected_diners > 0`。 |
| dietary_restriction | workspace_id、type、ingredient_key、severity | 用餐人群限制；过敏原为硬约束。 |
| kitchen_tool | workspace_id、tool_key | 厨具影响可做菜的筛选。 |
| ingredient | id、key、name、category、default_unit | `key` 全局唯一，作为匹配和替代基准。 |
| inventory_item | workspace_id、ingredient_id、quantity、unit、purchased_on、expires_on | `quantity >= 0`；过期品默认不参与可用库存。 |
| recipe | id、name、servings、duration_minutes、difficulty、image_source、tags | 图片及内容来源必须可追溯。 |
| recipe_ingredient | recipe_id、ingredient_id、quantity、unit、optional、substitutes | 配方食材明细。 |
| recipe_step | recipe_id、step_no、instruction、duration_minutes | `(recipe_id, step_no)` 唯一。 |
| meal_plan | workspace_id、start_date、days、status、constraints_snapshot | 保存生成时的约束快照以便解释。 |
| meal_plan_item | meal_plan_id、meal_date、meal_type、recipe_id、servings、score_breakdown | 同一餐位不重复菜谱。 |
| agent_run | workspace_id、meal_service_id、request_text、constraints、state、status | 保存 LangGraph 运行状态与版本。 |
| tool_trace | agent_run_id、tool_name、input_digest、status、duration_ms | 提供可观测性，不记录密钥。 |
| kiosk_device | workspace_id、site_id、device_id、token_hash、status、last_seen_at | 公共 PC 设备；只允许读取已发布菜单和提交反馈。 |
| feedback | device_id、meal_plan_id、rating、tags、comment、leftover_level、is_suspicious | 匿名反馈，无 `user_id`；评分 1–5。 |
| interaction_event | workspace_id、device_id、event_type、meal_plan_id、context | 记录终端提交与重置事件。 |

为兼容未来个人版，所有业务数据统一按 `workspace`（工作区）归属，并新增以下基础实体：

| 实体 | 关键字段 | 关系/约束 |
| --- | --- | --- |
| user | id、email、password_hash、display_name | 身份只存一次，不把用户类型固化在 user 表。 |
| workspace | id、name、kind、owner_id | MVP 固定 `organization`；保留 `personal` 供未来个人版。 |
| workspace_member | workspace_id、user_id、role、status | 唯一 `(workspace_id,user_id)`；角色为 `owner`、`manager`、`member`。 |

库存、菜单、Agent 运行、反馈及事件均可追溯到 `workspace_id`。管理端按工作区鉴权；评分终端通过受限设备令牌访问，不能成为普通工作区成员。

食材单位换算需维护独立的 `unit_conversion` 配置；无法安全换算的单位必须返回「需人工确认」，不能静默合并。

## 5. 规则引擎与菜单生成

### 5.1 Agent 决策流程

1. 将管理员自然语言转为结构化约束；缺少人数、餐次等关键字段时追问。
2. 调用工具读取站点、餐次、库存、临期食材和历史反馈摘要。
3. 召回菜谱并执行过敏原、厨具、时长等硬过滤。
4. 使用不同软目标权重生成临期优先、成本优先、满意度优先三种方案。
5. 按预计人数换算用量，计算热量估算、成本、库存缺口和采购清单。
6. 执行风险复核并向管理员解释取舍；人数、预算或替代食材变化时做 What-if 重规划。
7. 管理员明确选择并确认后才能发布。评分终端的聚合反馈在下一次规划时进入软评分。

建议的可解释分数（初版权重可配置）：

```text
score = 0.40 * expiring_ingredient_coverage
      + 0.25 * preference_match
      + 0.20 * time_fit
      + 0.10 * budget_fit
      + 0.05 * feedback_affinity
      - repeat_penalty
```

任一硬约束不满足即淘汰，不能用高分抵消。返回结果须包含 `score_breakdown`、命中临期食材、被过滤原因及缺少食材，供界面与测试使用。

### 5.2 Agent 工具契约

首批工具为：`get_meal_service_context`、`list_inventory`、`get_feedback_summary`、`search_recipe_candidates`、`filter_hard_constraints`、`scale_recipe_quantities`、`score_menu_options`、`estimate_nutrition_and_cost`、`build_procurement_list` 和 `publish_meal_plan`。

- 读取工具返回经 Pydantic 校验的 JSON，不返回 API Key、原始模型消息或不必要的个人信息。
- `publish_meal_plan` 是高风险副作用工具，必须携带管理员确认状态、工作区作用域和幂等键。匿名反馈通过独立 Kiosk API 写入，不由 Agent 代写。
- Agent 运行配置最大步骤数、超时和工具白名单；工具失败时停止写操作并返回可恢复的错误。
- UI 应展示结构化约束、多种方案、调用工具、耗时、警告和推荐依据，但不暴露内部提示词和密钥。
- LLM 不可用时返回规则基线方案；工具失败时标记对应节点并禁止发布不完整方案。

## 6. REST API（v1 草案）

统一前缀 `/api/v1`。成功响应为业务对象或 `{ "items": [], "meta": {} }`；错误格式为 `{ "code": "...", "message": "...", "details": [] }`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / PUT | `/workspaces/{workspace_id}/profile` | 查询或更新食堂档案、用餐限制、厨具。 |
| GET / POST | `/workspaces/{workspace_id}/inventory` | 查询或新增库存项。 |
| PATCH / DELETE | `/inventory/{item_id}` | 修改数量/日期或删除库存项。 |
| GET | `/recipes`、`/recipes/{recipe_id}` | 菜谱检索和详情。 |
| POST / GET | `/agent/runs`、`/agent/runs/{id}` | 创建/读取 Agent 运行、约束、轨迹和多方案。 |
| POST | `/agent/runs/{id}/revise` | 修改人数、预算或食材后增量重规划。 |
| POST | `/meal-plans/preview` | 按约束生成但不保存的多种菜单及解释数据。 |
| POST / GET | `/meal-plans`、`/meal-plans/{id}` | 保存并读取菜单计划。 |
| POST | `/shopping-lists/preview` | 根据计划和库存生成采购缺口。 |
| GET / POST | `/kiosk/current-menu`、`/kiosk/feedback` | 终端读取菜单并提交匿名反馈。 |
| GET | `/feedback/summary` | 返回聚合评分、标签、备注摘要与剩余等级。 |
| GET / POST | `/sites` | 查询或维护食堂站点。 |
| GET / POST | `/meal-services` | 查询或维护餐次与预计人数。 |
| POST | `/meal-plans/{id}/publish` | 管理员发布菜单。 |

Agent 请求至少关联 `workspace_id`、`site_id`、`meal_service_id` 和自然语言需求。返回值必须包含 `constraints`、`options`、`tool_trace`、`warnings` 和 `approval_status`。方案包含热量估算、成本、评分拆解和采购缺口。发布与反馈写接口使用 `Idempotency-Key`。

## 7. 前端页面与状态

- 管理员工作台：V1 使用预置管理员登录；真实成员邀请留到后续试点。
- 食堂档案：站点、餐次、预计人数、用餐限制与厨房条件；保存前展示硬约束提示。
- 食堂库存：按到期日排序，临期和过期状态显著区分，支持入库、消耗和编辑。
- Agent 规划：自然语言输入、缺字段追问、工具轨迹、多方案比较、What-if 修改和人工确认发布。
- 菜谱详情：封面、原料、缺口、步骤、总耗时、替代建议与来源。
- 采购清单：按品类归并，显示按人数放大后的所需量、现有量、缺少量及无法换算项。
- 公共 PC 自助终端：以 `/kiosk` 全屏显示当餐菜单和大按钮，支持快捷标签与可选备注；提交后感谢 2–3 秒并自动清空重置。

Pinia 只保存当前工作区、管理员会话、Agent 运行引用和短期 UI 状态；Kiosk 单独保存受限设备会话及当前餐次，不共享管理员状态。服务端数据以 API 为准。

## 8. 配置、安全与隐私

提交 `.env.example`，实际 `.env` 不入库。最低配置为 `DATABASE_URL`、`LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`、`CORS_ORIGINS`、`LOG_LEVEL`。V1 不提供本地模型配置；供应商切换只修改服务端环境变量。生产环境还应设置认证密钥、速率限制和受信任代理配置。模型策略见 [模型选型与部署策略](模型选型与部署策略.md)。

- API Key 仅保留在后端环境变量，禁止出现在前端构建产物、日志、异常详情与测试快照中。
- 所有资源按 `workspace_id` 鉴权；不得仅凭对象 ID 读取或修改他人数据。每一个 Repository 查询都必须接收工作区作用域。
- 过敏原/忌口数据按敏感偏好处理，日志只记录必要的匿名标识。
- 校验日期、数量、单位、评分和文本长度；对 Agent、发布与 Kiosk 反馈限流。原始备注脱敏并作为不可信输入处理。
- 菜谱图片、营养资料和替代关系须记录来源、许可和采集日期。

## 9. 本地开发、测试与交付

实施后应提供以下标准命令（以实际包管理器为准）：

```text
docker compose up --build
cd apps/api && pytest
cd apps/web && npm run lint && npm run test && npm run build
```

测试最低覆盖：结构化约束、缺字段追问、过敏原过滤、临期计算、人数换算、热量/成本、采购缺口、三方案评分、What-if、管理员确认、设备权限、Kiosk 自动重置和 Agent 工具失败回退。端到端测试至少验证「配置餐次 → Agent 多方案 → What-if → 管理员发布 → 连续两次匿名评分 → 下一轮读取反馈摘要」。

CI 建议分为 `lint`、`test-api`、`test-web`、`e2e`（可选）、`build`；PR 合并前至少要求 lint、单元测试和构建通过。数据库演进使用 Alembic 迁移，禁止依赖应用启动时自动改表。

## 10. 实施顺序与验收

1. 建立后端/前端骨架、环境样例、数据库迁移与 30–50 道可追溯种子菜谱。
2. 交付食堂站点/餐次、库存 CRUD、临期规则和菜谱详情。
3. 交付结构化约束、硬过滤、人数换算、热量/成本、三方案评分和采购计算。
4. 用 LangGraph 编排工具，完成缺字段追问、What-if、轨迹、降级与人工确认发布。
5. 交付公共 PC 匿名评分终端、自动重置、反馈摘要回流，再补 CI、演示脚本和发布说明。

V1 验收以如下场景为准：机关一食堂午餐 120 人、预算 900 元、花生限制、清淡偏好和临期番茄；Agent 返回三种可解释方案和准确采购缺口，可在人数改为 150 后重规划；管理员确认发布；餐厅公共 PC 自助终端连续收集两次匿名评分并自动重置；下一次规划能引用聚合反馈摘要；模拟模型超时后仍可返回规则基线。
