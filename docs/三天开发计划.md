# MealFlow V1：国庆 3–4 天双人开发计划

> 版本目标：国庆期间完成开发，国庆后用于 5–7 分钟现场演示。
> 产品主线：政府机关食堂运营决策 Agent。
> 开发方式：Lrio 与 Colin 使用 Vibe Coding 协作；AI 生成代码必须经过运行、测试和互审，不能以“生成完成”代替验收。

## 1. V1 成功标准

V1 不追求完整食堂 ERP，而要把一条有说服力的 Agent 决策闭环跑通：

```text
自然语言任务 → 结构化约束 → 自主调用工具 → 三方案比较
→ What-if 重规划 → 人工确认发布 → 公共终端反馈
→ 反馈进入下一轮规划 → 模型失败时规则降级
```

演示必须让观众看见 Agent 做了哪些判断、调用了哪些业务工具、为什么改变方案，以及哪些操作必须由人确认。单纯生成一段菜单文字不算完成。

开发资源按“Agent 70%、支撑页面 30%”分配。库存、采购、菜谱和 Kiosk 只实现支撑 Agent 闭环所需的最小功能，不扩展成完整管理系统。

## 2. 冻结范围

### 必须交付（P0）

- 预置“示例机关食堂”工作区、管理员账号、一个站点和午餐餐次。
- 20–30 道可追溯种子菜谱，包含食材、基础热量、份数、成本和简化做法。
- 库存、到期日期、临期提醒、预计人数、预算、口味和过敏原限制。
- 一个主 Agent：约束解析、缺字段追问、工具白名单、执行轨迹和状态展示。
- 临期优先、成本优先、满意度优先三种方案及评分拆解。
- 人数或预算变化后的 What-if 重规划。
- 确定性计算：批量用量、热量估算、成本、库存占用和采购缺口。
- 菜品详情：点击菜单可查看批量原料、热量和简化做法。
- 管理员明确确认后发布，未确认不得产生业务副作用。
- 餐厅门口公共 PC 自助终端：评分、快捷标签、可选备注、感谢页和自动清空。
- 反馈聚合进入下一次规划，并由 Agent 解释调整原因。
- LLM 超时/失败时返回规则基线方案，不阻断核心计算。
- 云端模型接入：千问 API 为主、DeepSeek API 备用、智谱为验证后候选；V1 不部署本地模型。

### 时间允许再做（P1，第 4 天优先）

- 登录页与简化角色提示、Agent 运行审计列表、反馈趋势小图表。
- Docker Compose、演示数据一键重置、关键链路 Playwright 冒烟测试。
- 采购清单 CSV 导出、终端维护 PIN、异常反馈峰值标记。
- 固定 Agent 评测集与结果页，展示约束正确率和工具成功率。

### 明确不做

干部职工手机端、真实员工账号、短信验证码、统一身份认证、真实采购下单、支付、排班、复杂 RBAC、多站点调拨、图像识别、多 Agent、模型微调、复杂 RAG、真实政务系统对接、本地模型、GPU/推理框架和生产级私有化部署均不进入 V1。

## 5. Vibe Coding 工作方式

1. 先写接口示例和验收用例，再让 AI 生成小范围实现；一次只生成一个可验证用户故事。
2. 要求 AI 解释修改文件、数据流和测试方法，禁止一次性改动整个项目后再排错。
3. 所有生成代码必须实际启动；接口用 Swagger/curl 验证，页面用浏览器走通。
4. 库存、金额、单位换算、过敏原和发布权限必须有人工检查及固定测试。
5. 每次达到里程碑立即打可回退提交；演示前冻结功能，只修阻断问题。

## 6. 进度与止损

- 每日 09:30 确认唯一演示目标，20:30 现场跑一遍，不以代码行数判断进度。
- Day 1 18:00 冻结数据模型和 API 名称；Day 2 18:00 冻结 Agent 返回结构。
- 优先级固定为：硬约束/计算正确性 > Agent 主链 > 人工确认 > 反馈闭环 > 降级 > UI 美化 > Docker。
- Day 2 中午模型调用仍不稳定时，保留模型负责约束解析，菜单候选与计算全部走确定性工具。
- Day 3 中午主链未通时，立即停止新增页面，用预置账号和种子数据保证闭环。

## 7. Definition of Done

每项功能必须能从页面操作、经过服务端校验、有自动化测试或可复现手工步骤、有 loading/empty/error 状态，并同步更新接口或数据文档。完整演示至少连续成功两次，且仓库、前端产物和日志中不存在模型密钥。
