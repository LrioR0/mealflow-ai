# MealFlow V1 演示验收标准

## 1. 演示数据

准备“示例机关食堂”组织工作区，含预置管理员 Lrio、机关一食堂、明日午餐（预计 120 人）和一台已注册公共 PC 自助终端。库存包含鸡蛋、番茄、土豆和鸡胸肉，其中番茄两天内到期；用餐限制包含花生过敏与清淡偏好；种子库至少 20 道可追溯的中式菜品。

## 2. 必过场景

1. 管理员能查看餐次、120 人、预算、限制和库存临期状态。
2. 输入“明天午餐 120 人，预算 900 元，清淡，优先消耗临期番茄，不能含花生”，Agent 输出经 Schema 校验的结构化约束；缺关键字段时会追问。
3. 页面显示 Agent 实际调用的上下文、库存、反馈、菜谱检索、硬过滤、换算、成本和采购工具及其状态摘要。
4. Agent 返回临期优先、成本优先和满意度优先三个方案，显示人均热量估算、评分拆解、推荐依据、风险和采购缺口。
5. 人数改为 150 或预算降低 200 元后，Agent 基于当前运行重规划；用量、成本和采购缺口随之变化。
6. 任何方案不得包含花生等硬限制；无法满足时返回冲突原因，不编造可用库存。
7. 点击菜品可查看批量原料、热量、简化做法和数据来源。
8. Agent 只能生成草案；管理员明确选择和确认后才能发布。
9. 公共 PC Kiosk 只能读取当前已发布菜单并提交匿名评分、快捷标签和可选备注。
10. 提交后感谢页显示 2–3 秒并自动清空；连续两次反馈不存在上一位输入残留。
11. 管理端看到聚合反馈；下一轮 Agent 能引用安全摘要解释菜单调整。
12. 模型超时或不可用时，系统明确降级并仍能输出规则基线方案、用量和采购缺口。
13. V1 通过服务端真实调用已冻结的云端模型 API；仓库和部署中不存在本地模型、推理服务或 GPU 依赖。

## 3. 可讲亮点验收

- 能回答“为什么推荐”：至少展示临期利用、预算匹配、历史反馈和风险中的三项依据。
- 能回答“如果条件变了怎么办”：现场完成一次 What-if，而不是重新输入整段提示词。
- 能回答“为什么不是传统系统”：自然语言目标被转成约束并自动编排多个工具，结果可解释、可调整、可审批。
- 能回答“模型出错怎么办”：确定性计算、硬规则、人工确认和降级链路清晰可见。
- 能回答“是否形成闭环”：公共终端反馈真实写入并影响下一轮软评分。

## 4. Agent 演示门槛

以下条件必须全部满足，否则即使管理页面完整也不能称为 V1 完成：

- 真实云端模型完成自然语言约束抽取，而不是前端写死字段。
- Agent 至少展示五个真实工具节点及输入/输出摘要。
- 三个方案必须来自不同软目标权重，并体现真实取舍，而不是仅更换标题。
- What-if 必须复用当前 Agent Run，相关用量、成本和采购数据同步变化。
- 过敏原等硬规则由确定性工具执行，模型不能覆盖。
- 发布前存在明确的 Human-in-the-loop 等待状态。
- 公共终端聚合反馈能改变下一轮软评分或解释。
- 模型超时后明确进入规则降级，不能返回伪造的“智能结果”。

## 5. 阻断发布问题

以下任一情况即不通过：跨工作区读取或修改数据；Kiosk 能进入管理端；未确认自动发布；过敏原进入结果；库存、人数换算或采购缺口错误；匿名备注直接作为指令进入 Agent；上一位终端输入残留；库存为负；页面无错误提示；模型密钥出现在仓库、日志或前端产物。

## 6. 演示稳定性

完整链路需在演示环境连续成功两次。V1 使用种子数据、预置管理员和云端模型 API；演示前 24 小时冻结主模型及配置。必须明确哪些能力是演示实现，不能声称已经在真实政府单位生产上线。
