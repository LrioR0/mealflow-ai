# 食序 MealFlow：政府机关食堂运营决策 Agent 产品定稿方案

> 文档状态：产品基线 v1.0  
> 产品类型：B2G 内部运营系统  
> 核心终端：管理员 PC Web + 餐厅公共 PC 自助终端（Kiosk）  
> V1 节奏：Lrio 与 Colin 在国庆期间 Vibe Coding 3–4 天，国庆后演示  
> 核心原则：Agent 负责理解、编排和解释；确定性工具负责事实、规则与计算；关键业务操作由人确认。

## 1. 产品定义

**食序 MealFlow** 是面向政府机关内部食堂的运营决策 Agent。系统根据就餐人数、库存、临期食材、饮食限制、预算、菜谱标准和历史反馈，自主调用业务工具，形成可解释的菜单与采购方案；食堂管理员审核后发布，用餐人员在餐厅门口的公共 PC 自助终端匿名反馈，反馈结果进入下一轮规划。

产品不是通用聊天机器人，也不是完整财务或采购 ERP。首期聚焦“菜单规划—库存利用—采购缺口—发布—反馈改进”这一条可验证主链路，并为后续对接现有政务系统、统一身份认证和采购系统预留接口。

V1 的国庆后演示以 Agent 为绝对主线，管理系统页面只是 Agent 的数据来源、工具载体和执行出口。5–7 分钟演示至少 70% 时间用于约束理解、真实工具调用、多方案决策、What-if、反馈改进和降级，不能把库存 CRUD 或菜单表格作为主要内容。统一讲解口径见 [V1 Agent 价值与演示口径](V1-Agent价值与演示口径.md)。

## 2. 建设背景与价值

### 2.1 典型问题

- 菜单依赖厨师或管理员个人经验，人员变化后难以稳定传承。
- 就餐人数、库存、采购和菜单分散管理，重复录入和沟通成本高。
- 临期食材发现不及时，容易产生浪费。
- 过敏原、民族饮食习惯和清淡需求缺少统一约束。
- 用餐反馈零散，难以转化为下一轮菜单决策依据。
- 通用大模型可能编造库存、用量、热量或安全结论，不能直接承担业务计算。

### 2.2 产品价值

- 将菜单规划从经验驱动升级为“规则 + 数据 + Agent”辅助决策。
- 缩短排餐和采购清单整理时间。
- 提高临期食材利用率，降低剩余与浪费。
- 对过敏原和明确饮食限制执行硬过滤。
- 保留每次推荐依据、工具调用和人工确认记录，便于审计和复盘。
- 形成菜单发布、公共终端反馈和持续优化的闭环。

### 2.3 区别于传统管理系统

| 传统食堂管理系统 | MealFlow V1 |
| --- | --- |
| 要求管理员逐页查询人数、库存、菜单和反馈后自行判断。 | 管理员描述目标，Agent 主动读取上下文并编排多个业务工具。 |
| 主要提供固定表单、CRUD 和静态报表。 | 根据人数、预算、库存或反馈变化执行 What-if 重规划。 |
| 给出记录结果，但很少解释推荐原因。 | 展示约束、工具轨迹、评分拆解、风险和方案取舍。 |
| 规则散落在人和流程中，模型输出也可能不可控。 | 硬约束和计算由确定性服务执行，Agent 不能绕过规则。 |
| 自动化操作可能缺少人工责任边界。 | 菜单发布、采购和库存变更必须由授权人员确认并留痕。 |
| 反馈通常停留在报表。 | 聚合反馈成为下一次规划的软信号，并生成可解释调整建议。 |

传统系统的价值是“把业务记录下来”，MealFlow Agent 的核心价值是“基于这些记录完成跨模块决策，并随着条件变化重新规划”。因此 V1 是否成功，不以页面数量衡量，而以 Agent 能否独立完成多步、可解释、可审批、可降级的决策过程衡量。

## 3. 用户与终端

| 角色 | 主要终端 | 核心权限 |
| --- | --- | --- |
| 食堂管理员 | PC Web | 配置餐次人数、调用 Agent、比较方案、确认发布、查看反馈。 |
| 仓库管理员 | PC Web / Pad | 食材入库、消耗、盘点、临期与异常处理。 |
| 采购人员 | PC Web | 查看采购缺口、确认数量、导出或提交采购清单。 |
| 食堂负责人/审批人 | PC Web，后续兼容手机审批 | 审核菜单、预算和采购方案，查看运营报表。 |
| 厨师/后厨人员 | PC Web / Pad | 查看已确认菜单、批量用料和标准化做法。 |
| 用餐人员 | 餐厅公共 PC 自助终端 | 查看当餐菜单、热量与过敏原，匿名提交评分、标签和可选备注。 |
| 系统管理员/审计人员 | PC Web | 组织、角色、设备、模型配置、操作日志和 Agent 运行审计。 |

公共评分端采用浏览器全屏 Kiosk 模式，可运行在 Windows/Linux PC、触摸一体机或类似银行自助机的设备上。它使用独立受限设备令牌，不是管理员工作站，也不提供后台导航。V1 不建设干部职工手机端和个人账号体系。

## 4. 核心业务闭环

```text
管理员配置站点、餐次、预计人数、预算和饮食限制
                  ↓
管理员用自然语言描述本次运营目标
                  ↓
Agent 解析结构化约束并读取库存、临期食材、菜谱和反馈
                  ↓
确定性工具完成硬过滤、人数换算、热量/成本和采购缺口计算
                  ↓
Agent 返回临期优先、成本优先、满意度优先三种可解释方案
                  ↓
管理员进行 What-if 调整并选择方案
                  ↓
负责人确认后发布菜单与采购清单
                  ↓
用餐人员在餐厅门口公共终端提交餐后反馈
                  ↓
系统聚合评分、标签、备注和剩余情况
                  ↓
下一次 Agent 规划读取反馈摘要并解释调整原因
```

## 5. Agent 产品能力

### 5.1 约束理解

管理员可以输入：

> 明天机关一食堂午餐 180 人，预算 1500 元，整体清淡，不能含花生，优先消耗两天内到期的番茄，后厨 90 分钟内完成。

Agent 转换为经 Schema 校验的站点、餐次、人数、预算、口味、过敏原、临期优先级、时间上限等字段。缺少关键字段时必须追问，不得自行猜测。

### 5.2 工具编排

Agent 可调用餐次、库存、临期、反馈、菜谱检索、硬约束过滤、批量换算、热量/成本估算、菜单评分和采购缺口等白名单工具。界面展示工具名称、执行状态、耗时、结果摘要和错误，但不暴露内部提示词或密钥。

### 5.3 多方案与 What-if

同一组硬约束下至少生成：

- 临期优先：最大化临期食材消耗。
- 成本优先：在预算内降低采购成本。
- 满意度优先：提高历史高评分菜品权重并控制重复。

管理员可继续输入“人数改为 220”“预算减少 300 元”“鸡胸肉换成其他蛋白质”等条件，Agent 基于当前状态重算受影响节点。

### 5.4 人工确认

Agent 可以生成、比较和解释方案，但不能未经确认发布菜单、提交采购、扣减库存或修改硬约束。所有副作用操作保存操作者、时间、工作区、对象、变更前后值和 Agent 运行 ID。

### 5.5 反馈闭环

Agent 读取按餐次聚合的平均分、标签占比、备注安全摘要和剩余等级。例如：

> 上次“土豆时蔬”评分 2.9，主要标签为“太咸”，剩余量较高；本次降低其满意度权重，并建议调整调味标准。

反馈属于软信号，不得突破过敏原、禁用食材和食品安全规则。

### 5.6 降级与评测

模型超时或不可用时，系统返回规则引擎的基线方案和明确提示，核心库存与采购计算仍可使用。固定评测集覆盖正常规划、缺字段追问、过敏原冲突、库存不足、预算变化、人数变化、工具失败、模型超时和管理员拒绝发布。

## 6. 功能范围

### 6.1 管理员 PC Web

- 工作区、机关食堂站点与餐次。
- 预计人数、预算、饮食限制和后厨能力。
- Agent 自然语言规划、工具轨迹和缺字段追问。
- 三种方案对比、热量、成本、库存占用和采购缺口。
- 菜品详情、批量用料、标准化做法和来源。
- What-if 重规划、人工确认、菜单发布和操作审计。
- 库存入库、消耗、盘点、临期和过期提醒。
- 采购清单汇总、确认与导出。
- 评分、反馈标签、剩余等级和趋势分析。

### 6.2 公共 PC 自助评分终端

- 显示当前已发布餐次、菜品、主要食材、人均热量估算和过敏原提示。
- 提供大尺寸总体评分按钮、快捷标签与可选文字备注。
- 提交后显示感谢页 2–3 秒，随后清空全部输入并回到初始页面。
- 使用设备频率限制、冷却时间、重复内容检测和异常峰值标记降低刷票风险；匿名模式不承诺严格一人一票。
- 页面不提供后台导航，退出全屏模式需要管理员操作或终端维护口令。

### 6.3 后厨/仓库辅助页

- 已发布菜单与批量备料清单。
- 菜品分步做法、关键时间和安全提示。
- 实际用量、剩余量和库存扣减确认。

## 7. 非功能与政务场景要求

### 7.1 部署与模型

- V1 只调用国产云端模型 API，不下载模型、不配置 GPU、不做本地或内网模型部署。
- V1 默认使用千问 API，DeepSeek API 作为备用；智谱 API 保留为经固定用例验证后的可替换候选。
- 模型通过统一 Provider 接口接入，切换供应商不修改库存、菜单、采购等业务代码。
- V1 只使用演示种子数据；真实政务数据不得发送到未经批准的外部模型。
- V2 继续完善云端 Provider、评测与故障转移；V3 再按客户安全和算力条件评估私有化部署。
- 正式环境使用 PostgreSQL 或经项目适配验证的数据库；SQLite 仅用于演示。
- 支持模型不可用时的规则降级，不因模型故障阻断基础业务。

### 7.2 安全和审计

- 组织、站点和数据按工作区隔离。
- 管理员、仓库、采购、审批、审计等角色采用最小权限。
- 登录、菜单发布、采购确认、库存修改和 Agent 工具调用均记录审计日志。
- 密钥、令牌和数据库凭据由服务端配置管理，禁止进入前端和 Git。
- 公共终端只展示已发布数据；不采集姓名、手机号等身份信息，反馈仅以聚合形式进入 Agent。
- 文字备注进行限长、脱敏、敏感内容处理和提示注入防护。

### 7.3 可用性

- 关键写操作幂等并提供明确确认。
- Agent 运行支持超时、重试、取消和可恢复错误。
- 所有页面具备 loading、empty、error 和 retry 状态。
- 重要规则与计算具有单元测试；核心链路具有端到端测试。

## 8. 技术基线

- 管理端/公共终端：Vue 3、TypeScript、Vite、Pinia、Element Plus；同一前端工程以 `/admin` 与 `/kiosk` 路由和独立布局区分。
- API：FastAPI、Pydantic、SQLAlchemy、Alembic。
- Agent：LangGraph 状态机、LangChain 工具适配、结构化输出。
- 数据：演示使用 SQLite，正式部署使用 PostgreSQL；菜谱、库存和规则数据结构化保存。
- 测试：Pytest、Vitest、Playwright；Agent 使用固定输入与工具 Mock 评测。
- 部署：Docker Compose 演示，正式环境按机关基础设施要求适配。

采用模块化单体，不在首版拆微服务。Agent 通过 Application Service 调用业务能力，不能绕过 Service 直接访问数据库。

## 9. MVP 演示场景

1. 先说明管理员过去需要人工在人数、库存、菜谱、预算和反馈之间反复核对。
2. 管理员输入一个包含人数、预算、清淡、花生限制和临期番茄的自然语言任务。
3. Agent 展示结构化约束，并实际调用餐次、库存、反馈、菜谱、硬过滤、换算、成本和采购工具。
4. Agent 返回临期优先、成本优先和满意度优先三种方案，说明推荐依据、被淘汰方案和风险。
5. 管理员将人数由 120 改为 150，再降低预算；Agent 保留上下文并重算用量、成本和采购缺口。
6. 管理员查看菜品详情验证数字来源，随后选择方案并确认发布。
7. 两位用餐人员在公共 PC 自助终端连续反馈，页面自动清空。
8. 下一轮规划读取聚合反馈，解释“份量少”或“太咸”如何影响新方案。
9. 模拟模型超时，展示规则基线仍可完成硬过滤与计算。

## 10. 分阶段路线

### 阶段一：可演示 MVP

一个机关食堂、一个管理员、一个午餐餐次、20–30 道菜谱、库存、三方案 Agent、What-if、人工发布、公共终端匿名反馈和规则降级。

### V2：试点增强

统一身份认证、仓库/采购/审批角色、多餐次、真实审计、反馈趋势、菜谱 SOP RAG、设备和异常监控、PostgreSQL，以及千问/DeepSeek/智谱云端 Provider 的评测、故障转移和成本统计。V2 仍不部署本地模型。

### V3：系统集成与私有化评估

按实际项目条件对接政务统一门户、采购系统、门禁或就餐人数来源、消息通知和既有机关事务平台。仅在客户要求数据不出域且具备算力与运维条件时，评估内网或专有云模型；任何对接和私有化均以项目审批、接口授权和业务评测为前提。

### 阶段四：智能运营

人数预测、浪费风险预测、采购量建议、跨站点分析和定时生成菜单草案。只有在单 Agent 效果和可观测性稳定后，才评估菜单、采购、库存等子 Agent。

## 11. 验收指标

| 类别 | MVP 指标 |
| --- | --- |
| 安全规则 | 过敏原和禁用食材过滤通过率 100%。 |
| 计算正确性 | 人数换算和采购缺口固定用例通过率 100%。 |
| Agent | 固定评测集结构化约束正确率不低于 90%，失败可降级。 |
| Agent 证据 | 至少展示 5 个真实工具节点、3 种方案、1 次有状态重规划和 1 次反馈驱动调整。 |
| 可解释性 | 每个方案包含约束、工具轨迹、评分拆解、热量/成本和风险。 |
| 人工控制 | 未经管理员确认不得发布或修改库存。 |
| 终端反馈 | 连续提交数据不残留；聚合结果可进入下一次规划。 |
| 性能 | 普通业务接口目标 2 秒内；Agent 规划给出进度并在配置超时内结束。 |

V1 不虚构“节省多少成本”等生产结论。V2 试点应采集规划耗时、人工查询次数、临期覆盖率、预算偏差、方案一次通过率、剩余等级、Agent 降级率和人工接管率，使用真实基线验证价值。

## 12. 项目表述边界

该方案可以作为来源于真实政务业务经验的团队项目或产品原型，但在未获得真实政府客户授权、未正式部署和未产生生产数据前，不应表述为“已在某政府单位上线”。对外可描述为“基于政府机关食堂场景设计的企业级 Agent 项目”或“政务行业场景原型”。

## 13. 最终决策

- 产品只做 B2G 主线，不同时开发完整 C 端。
- 管理员使用 PC Web；用餐人员使用餐厅公共 PC 自助终端，V1 不开发手机端。
- V1 模型只采用云端 API：千问为主、DeepSeek 备用、智谱为可替换候选；不做本地部署。
- 以一个主 Agent 和确定性工具为首版核心，不堆叠多 Agent。
- Agent 的亮点是结构化理解、工具编排、多方案、What-if、人工确认、反馈闭环、审计和降级。
- 数据模型保留个人工作区扩展能力，但不进入当前页面、演示和验收范围。
