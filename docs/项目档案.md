# 食序 MealFlow：项目档案（历史家庭版方案）

> 本文保留项目最初的家庭菜单助手立项方案，供个人版未来扩展时参考。自 2026-09-30 起，国庆 MVP 的正式主线改为企业食堂智慧运营助手；当前范围、分工和验收以 [三天开发计划](三天开发计划.md)、[B 端主线与 C 端兼容架构](多租户产品设计.md)、[MVP 验收标准](mvp.md) 为准。本文与这些文档冲突时，后者优先。

## 1. 项目定位

**食序 MealFlow** 是面向情侣、合租室友和小家庭的「菜单规划、食材管理与烹饪指导智能体」。

项目不做一个只会闲聊的菜谱 Demo，而是围绕日常家庭做饭的完整闭环：用户维护成员偏好和家中食材；系统识别临期食材、时间、预算和饮食限制；智能体调用确定性工具给出可执行菜单；用户查看菜品图片和详细做法，并获得购物清单；最终通过做饭反馈持续改善推荐。

## 2. 要解决的问题

- 每天不知道吃什么，两人偏好、忌口和时间安排不同。
- 冰箱食材容易遗忘、过期或重复购买。
- 菜谱只有成品图，不知道家里现有食材能否完成、缺什么、需要多久。
- 购物清单和菜单计划分散，协作成本高。
- 通用大模型容易编造食材库存、营养数值或烹饪时长，缺少可解释性。

## 3. 目标用户与核心场景

### 目标用户

- 共同生活的情侣（第一目标用户）。
- 合租室友、小家庭。

### 首个演示场景

1. 两名成员已经填写口味、忌口、预算和常用厨具。
2. 冰箱中有鸡蛋、番茄、土豆、鸡胸肉等食材，部分食材即将过期。
3. 用户输入「今晚两个人，30 分钟内，优先消耗临期食材，清淡一点」。
4. Agent 调用库存、候选菜谱、评分和购物清单工具。
5. 页面展示一餐或三日菜单、菜品图片、原因解释、详细步骤和购物清单。
6. 两人记录「做了 / 没做」「评分」「实际耗时」「剩余食材」，为后续推荐积累数据。

## 4. 国庆演示版（MVP）范围

### 必做功能

1. **家庭档案**：两位成员的口味、忌口/过敏原、饮食目标、预算、常用厨具。
2. **冰箱与食材库存**：手工新增、编辑、消耗食材；记录数量、单位、购买日和保质/到期日；临期提示。
3. **结构化菜谱库**：首批 30–50 道中式家常菜；每道含食材、用量、步骤、时长、难度、标签、营养估算、封面图片。
4. **菜单规划**：输出一餐和三日计划；硬性过滤过敏原、明确忌口和时间上限；优先使用临期食材。
5. **烹饪指导**：菜品封面图、食材清单、缺失食材、分步做法、总耗时、替代建议。
6. **购物清单**：按菜单和现有库存自动汇总缺少的食材。
7. **Agent 对话与可解释性**：用户自然语言提出需求；展示本次调用的工具、约束和推荐理由。
8. **反馈闭环**：收藏、接受/拒绝、已烹饪、评分、实际耗时和剩余情况。

### 首版明确不做

- 自动识别冰箱照片、条码扫描。
- 实时商超价格、下单和支付。
- 医疗、减脂或疾病诊断建议。
- 社区、复杂关注关系或复杂推荐算法。
- 直接让大模型编造库存、营养或安全结论。

## 5. 业务模块

| 模块 | 业务功能 | 首版实现 |
| --- | --- | --- |
| 家庭与成员 | 偏好、忌口、预算、厨具 | 表单 + SQLite |
| 食材库存 | 入库、消耗、临期提醒 | 手工维护 + 到期规则 |
| 菜谱中心 | 菜谱检索、详情、图文做法 | JSON/SQLite 种子数据 |
| 菜单规划 | 一餐/三日菜单、约束过滤、排序 | 规则引擎 + Agent 调用 |
| 购物清单 | 缺货计算、按品类汇总 | 确定性计算工具 |
| 烹饪页 | 图片、步骤、计时、替代建议 | 前端详情页 |
| 反馈与画像 | 收藏、评分、已做、剩余 | 事件表，为 ML 预留 |
| 智能体编排 | 识别意图、选工具、生成解释 | LangGraph + LLM API |

## 6. Agent 设计原则

### 可由大模型完成

- 理解用户的自然语言约束。
- 决定何时调用哪个工具。
- 根据工具结果生成自然、可读、有依据的解释。
- 在菜谱知识库中做语义问答，例如「没有蚝油能否替代」。

### 必须由确定性工具完成

- 过敏原和明确忌口过滤。
- 食材库存、保质期、临期判断。
- 菜谱食材缺口和购物清单计算。
- 营养数据和规则评分。
- 数据库写入与权限校验。

### 首批工具

```text
get_household_profile     获取家庭偏好与硬约束
list_fridge_inventory    获取当前库存与临期食材
search_recipe_candidates 搜索结构化菜谱候选
score_recipes            按匹配度、临期、耗时等规则评分
calculate_nutrition      汇总营养估算
build_shopping_list      计算缺失食材并生成购物清单
save_meal_plan           保存菜单计划
save_feedback            保存烹饪与评分反馈
```

## 7. 技术方案

### 前端

- Vue 3、Vite、TypeScript、Pinia、Element Plus。
- 页面：家庭档案、冰箱库存、菜单规划、菜谱详情、购物清单、反馈页。

### 后端

- FastAPI、Pydantic、SQLAlchemy。
- SQLite 作为 MVP 数据库；稳定后迁移 PostgreSQL。
- APScheduler 用于每日临期提醒（可选）。

### 智能体与知识检索

- LangChain + LangGraph 编排工作流与工具调用。
- 首版优先使用 API 大模型（如通义千问或智谱），通过后端 `.env` 配置；密钥绝不提交 Git，也不下发前端。
- 语义检索后续使用本地 Embedding + Chroma，存放烹饪技巧、食材处理、替代关系等非结构化知识。
- RAG 不替代结构化菜谱、库存和营养事实数据。

### 部署与质量

- Docker Compose 一键启动前后端。
- Pytest 做后端规则测试；前端完成关键交互手工验收。
- README、演示脚本、接口文档、种子数据和截图是开源项目的必备交付物。

## 8. 数据与安全边界

- 用户身份信息只保存实现功能所需的最小字段。
- 忌口与过敏原是硬约束，永远优先于模型推荐。
- 营养字段均标识为「估算」，不提供医疗/诊断建议。
- 首版食材数据和图片确保有可再分发的来源或自行制作；保留来源信息。
- API Key 写在 `.env`，仓库仅提交 `.env.example`。

## 9. 机器学习演进路线

首版不依赖机器学习也能正确工作；先用规则实现可解释的闭环，同时收集高质量反馈数据。

### 需要收集的事件

- 推荐曝光、点击、接受/拒绝、收藏。
- 是否实际烹饪、评分、实际耗时、剩菜/浪费情况。
- 菜谱、场景、时间、家庭偏好和库存特征。

### 后续可落地的模型

| 业务问题 | 目标 | 可从课程知识起步的技术 |
| --- | --- | --- |
| 个性化排序 | 预测某菜单被接受/喜欢的概率 | Logistic Regression、Random Forest，后续 LightGBM |
| 实际烹饪耗时 | 预测做完菜所需时间 | Ridge Regression、Random Forest Regressor |
| 食材浪费预警 | 判断食材是否高风险被浪费 | 分类模型、特征工程 |
| 采购量建议 | 预测某食材未来需求 | 回归与时间序列特征 |
| 家庭口味分群 | 发现偏好相近的菜谱类别 | K-Means |
| 食材图像识别 | 后续自动录入冰箱食材 | 预训练视觉模型/API，后续 YOLO/CLIP |

机器学习只负责概率预测和个性化排序，不能突破过敏原、忌口、库存真实性和安全边界；规则引擎始终保留为兜底。

## 10. 从 0 到 1 开发顺序

### 第 0 天：定边界

- 写清楚首个演示脚本和验收标准。
- 建仓库、建立 Issue 和基础文档。

### 第 1 天：项目骨架与数据模型

- 建立 `apps/api` 与 `apps/web`。
- 定义成员、库存、菜谱、菜单、反馈等数据模型。
- 导入首批菜谱种子数据。

### 第 2 天：基础业务页面

- 实现成员偏好、库存、菜谱列表与详情接口/页面。

### 第 3 天：规则引擎

- 完成硬约束过滤、临期优先、时间/预算评分和购物清单。
- 为规则写单元测试。

### 第 4 天：菜谱图文体验

- 补齐菜品图片、详细做法、缺失食材和步骤页。

### 第 5 天：接入 Agent

- 以 LangGraph 编排工具。
- 接入一个 API 模型，输出菜单与推荐理由。

### 第 6 天：联调与反馈

- 完成端到端演示链路、错误提示、反馈记录。

### 第 7 天：交付

- Docker Compose、README、接口文档、演示录屏与项目截图。

## 12. 协作方式

- 每次只完成一个小而可验收的用户故事：实现 → 运行 → 测试 → 人工从业务角度验收 → Git 提交。
- 建议提交信息：`feat: add household profile`、`feat: add refrigerator inventory`、`feat: add recipe scoring`、`feat: add meal planning agent`。
- 两人可分工：一人重点负责后端、规则、Agent 与数据；另一人重点负责前端、菜谱内容、图片、交互和演示材料；关键接口共同评审。
