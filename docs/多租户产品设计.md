# B 端主线与 C 端兼容架构

## 决策

国庆 MVP 只交付 B 端「智慧食堂运营助手」，不交付完整 C 端家庭产品。底层采用工作区模型以兼容未来个人版，避免日后重写数据隔离与权限；但当前界面、演示数据和验收只围绕企业食堂。

```text
user ──< workspace_member(role) >── workspace(kind: organization | personal)
                                          └── site ── meal_service
                                              └── inventory / meal_plan / feedback
```

国庆版本预置一个 `organization` 工作区和两个演示身份（`manager`、`member`）。不开发真实注册、登录或邀请，但每个业务查询仍强制使用已验证的 `workspace_id`。`personal` 是已保留的枚举值和迁移方向，不提供入口或页面。

## B 端角色和核心流程

| 角色 | 国庆 MVP 权限 | 后续可扩展 |
| --- | --- | --- |
| manager | 管理站点/餐次、库存、菜单预览、保存、发布、查看反馈 | 采购审批、成员管理、数据报表。 |
| member | 查看已发布菜单、提交评分与剩余反馈 | 订餐、忌口维护、通知。 |

管理员配置「总部食堂—午餐—120 人」后生成菜单；规则引擎按人数换算用量、过滤限制、优先临期库存、计算采购缺口；管理员确认发布；员工查看和反馈。这个链路是唯一演示主线。

## C 端未来接入

个人版创建 `personal` 工作区并复用 `workspace_id`、库存、菜谱、规则和反馈。差异仅在 `PlanningContext`：食堂传站点、餐次、预计人数和限制汇总；个人传家庭成员和份数。个人版不应反向影响食堂 MVP 的接口、页面或验收。

## 隔离要求

所有隔离数据带 `workspace_id`；Repository 每个查询都带工作区条件；服务端先验证成员关系，再执行业务操作。不能由前端单独决定角色或信任任意 `workspace_id`。规模增长后可迁移到 PostgreSQL 的 Row-Level Security。
