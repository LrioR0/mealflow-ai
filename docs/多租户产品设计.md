# B 端主线与 C 端兼容架构

## 决策

V1 只交付 B2G「政府机关食堂运营决策 Agent」，不交付完整 C 端家庭产品。底层采用工作区模型以兼容未来个人版，避免日后重写数据隔离与权限；当前界面、演示数据和验收只围绕机关食堂。

```text
user ──< workspace_member(role) >── workspace(kind: organization | personal)
                                          └── site ── meal_service
                                              └── inventory / meal_plan / feedback
```

V1 预置一个 `organization` 工作区和一个管理端身份（`manager`），另注册一台受限公共 PC 自助终端。用餐者不属于工作区成员，也不需要员工账号。每个管理端查询仍强制使用已验证的 `workspace_id`；`personal` 是未来迁移方向，不提供入口或页面。

## B 端角色和核心流程

| 角色 | 国庆 MVP 权限 | 后续可扩展 |
| --- | --- | --- |
| manager | 管理站点/餐次、库存、Agent 规划、菜单确认发布、查看聚合反馈 | 采购审批、成员管理、数据报表。 |
| kiosk device | 公共 PC 只读取当前已发布菜单、提交匿名反馈 | 多终端管理、离线缓存、设备健康监控。 |

管理员配置「总部食堂—午餐—120 人」并向 Agent 描述目标；Agent 编排规则与计算工具，返回多种方案和 What-if 结果；管理员确认发布；餐厅出口的公共终端匿名收集反馈并自动重置。这个链路是唯一演示主线。

## C 端未来接入

个人版创建 `personal` 工作区并复用 `workspace_id`、库存、菜谱、规则和反馈。差异仅在 `PlanningContext`：食堂传站点、餐次、预计人数和限制汇总；个人传家庭成员和份数。个人版不应反向影响食堂 MVP 的接口、页面或验收。

## 隔离要求

所有隔离数据带 `workspace_id`；Repository 每个查询都带工作区条件；服务端先验证成员关系，再执行业务操作。不能由前端单独决定角色或信任任意 `workspace_id`。规模增长后可迁移到 PostgreSQL 的 Row-Level Security。
