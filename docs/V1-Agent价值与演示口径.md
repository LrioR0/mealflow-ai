# MealFlow V1：Agent 价值与演示口径（最终基线）

## 1. 一句话定义

MealFlow 是政府机关食堂运营决策 Agent：管理员只需描述目标，Agent 就会自主读取餐次、库存、临期食材和历史反馈，调用确定性工具生成多套菜单及采购方案，在条件变化时重规划，并在人工确认后形成反馈闭环。

V1 的主角是 Agent。库存、菜单、采购和公共评分页面是 Agent 获取事实、执行决策和验证闭环的业务工具，不是项目的展示中心。

## 2. 真正解决的问题

| 业务痛点 | 传统处理方式 | Agent 解决方式 | V1 现场证据 |
| --- | --- | --- | --- |
| 排餐依赖管理员和厨师经验 | 人工在库存表、菜谱和人数之间反复核对 | 理解自然语言目标并主动聚合多源数据 | 一句话生成经校验的结构化约束和执行计划 |
| 多目标互相冲突 | 人工在成本、临期、满意度之间凭经验取舍 | 在相同硬约束下生成三套策略并解释权衡 | 临期/成本/满意度方案对比和评分拆解 |
| 人数、预算临时变化 | 重新算用量、成本和采购清单 | 保留上下文，只重算受影响节点 | 120→150 人或预算降低后的 What-if |
| 临期库存容易浪费 | 靠人工查看到期日后临时调整菜单 | 主动发现临期食材并提高利用权重 | 展示番茄到期信息和临期覆盖依据 |
| 过敏原与业务计算不允许出错 | 依赖人工记忆或表格公式 | Agent 编排确定性工具，硬约束不可被模型覆盖 | 花生菜品被过滤，计算结果来自工具而非模型编造 |
| 反馈停留在统计报表 | 管理员看完分数后自行决定如何改 | 将聚合反馈转成下一轮软评分和调整理由 | 公共终端反馈后，下一轮解释“太咸/份量少”如何影响方案 |
| 大模型不稳定、责任不清 | 聊天结果不可审计，可能直接执行 | 工具轨迹可见、写操作需审批、失败可降级 | 展示 trace、确认发布和模型超时降级 |

## 3. V1 的七个 Agent 亮点

1. **自然语言目标理解**：把模糊需求转换为人数、预算、口味、过敏原、临期优先级和时限等结构化约束；信息不足时追问。
2. **自主工具选择与编排**：模型不是一次性回答，而是按任务选择餐次、库存、反馈、菜谱、过滤、换算、成本和采购工具，多步完成目标。
3. **多目标决策**：对同一问题生成临期优先、成本优先、满意度优先三套方案，并呈现无法同时最优的取舍。
4. **有状态重规划**：记住当前运行上下文；人数、预算或食材变化后只重算受影响部分，形成可观察的 What-if 能力。
5. **可解释与可追溯**：展示使用了哪些事实、调用了哪些工具、淘汰了什么方案、为何推荐以及存在什么风险。
6. **Human-in-the-loop**：Agent 可以建议和准备草案，但菜单发布、采购确认和库存修改必须由人决定。
7. **反馈闭环与降级**：公共终端反馈进入下一次规划；模型失败时确定性规则仍保证核心业务可用。

## 4. 与传统系统、普通聊天机器人的区别

| 判断项 | 传统管理系统 | 普通大模型聊天框 | MealFlow Agent |
| --- | --- | --- | --- |
| 用户输入 | 固定表单 | 自然语言 | 自然语言 + 业务上下文 |
| 数据获取 | 用户逐页查询 | 通常不知道真实业务数据 | 自主调用受控工具读取实时业务数据 |
| 计算方式 | 固定规则/人工 | 容易直接生成数字 | 确定性工具计算，模型只编排与解释 |
| 任务过程 | 预设固定流程 | 一次性文本回答 | 有状态、多步骤、可追踪执行 |
| 条件变化 | 用户重新操作 | 重新问一遍，前后可能不一致 | 基于当前状态进行 What-if 重规划 |
| 安全边界 | 权限控制 | 通常缺少业务审批 | 工具白名单 + 硬规则 + 人工确认 |
| 反馈利用 | 形成报表 | 无稳定业务记忆 | 聚合后进入下一轮软评分和解释 |
| 失败处理 | 固定错误提示 | 可能继续编造 | 重试、备用 Provider、规则降级 |

## 5. 什么才算演示出了 Agent

演示必须同时出现以下证据：

- 输入一条包含多重目标的自然语言任务。
- Agent 输出结构化约束，并在缺字段时主动追问。
- 至少显示五个真实工具节点及结果摘要，不播放伪造的固定动画。
- 给出至少两种存在明显取舍的方案，V1 目标为三种。
- 现场修改一个条件并重规划，相关数字同步变化。
- 展示一个硬约束淘汰过程，例如花生过敏。
- 管理员确认前不能发布。
- 公共终端反馈影响下一轮方案解释。
- 模拟模型故障并展示规则降级。

如果只是展示库存 CRUD、菜单表格、采购清单，或者输入一句话后直接出现固定菜单，均不算完成 Agent 演示。

## 6. 演示时间分配

5–7 分钟演示中，至少 70% 时间用于 Agent：

- 30 秒：问题与定位。
- 3 分钟：约束理解、工具轨迹、三方案和解释。
- 1 分钟：What-if 重规划。
- 40 秒：人工确认和发布。
- 50 秒：公共终端反馈与下一轮调整。
- 30 秒：模型故障降级与总结。

库存、采购和菜谱页面只在解释工具事实来源或执行结果时展示，不单独进行长时间 CRUD 演示。

## 7. 对外表述

推荐说法：

> 我们构建了一个面向政府机关食堂场景的运营决策 Agent。它通过大模型理解复杂目标，编排库存、菜谱、成本、营养和反馈工具，生成可解释的多方案决策；当人数或预算变化时能够有状态重规划，并通过人工审批、反馈闭环和规则降级保证业务可控。

不得声称已在真实政府单位生产上线，也不将规则计算包装成模型能力。项目亮点在于“模型负责决策编排，工具负责可信执行”，而不是调用了某一个具体大模型。

## 8. 后续可量化价值指标

V1 演示能力，不虚构生产收益；后续试点再采集以下指标形成真实价值证明：

- 从提出排餐任务到形成可审批方案的平均耗时。
- 管理员为一次规划手工查询或切换页面的次数。
- 临期食材被菜单覆盖的重量与比例。
- 实际采购成本与预算偏差。
- 菜单方案一次通过率和平均修改次数。
- 菜品评分、负面标签和剩余等级的变化趋势。
- Agent 工具成功率、降级率和人工接管率。
