# MealFlow Agent 设计

## 1. 定位

MealFlow 不是“食堂管理系统加聊天框”，而是政府机关食堂运营决策 Agent。管理员用自然语言描述目标，Agent 将需求转为结构化约束，自主选择只读和确定性计算工具，比较菜单方案、解释取舍并等待管理员确认。库存真实性、过敏原过滤、人数换算、热量估算和采购缺口由确定性服务提供，LLM 不直接编造。

V1 的判断标准不是“有没有接入大模型”，而是系统是否形成了 `感知业务状态 → 制定计划 → 调用工具 → 检查结果 → 根据变化重规划 → 等待人确认` 的完整决策循环。

## 2. 要解决的决策任务

Agent 将原本需要管理员跨页面、跨表格完成的工作压缩成一个可追踪任务：同时考虑预计人数、库存与临期、预算、过敏原、后厨时长和历史满意度，生成多种可执行方案及采购缺口。它重点减少信息搜集、重复计算和方案权衡成本，不替代食品安全责任人或审批人。

## 3. V1 Agent 能力

1. **结构化约束**：提取站点、餐次、人数、预算、时长、口味、过敏原和临期优先级；缺少关键字段时向管理员追问。
2. **工具编排**：读取餐次、库存和历史反馈，检索菜谱，执行硬过滤、批量换算、评分、成本与采购计算。
3. **多方案比较**：至少给出临期优先、成本优先和满意度优先三种方案，并展示分数拆解与取舍。
4. **What-if 重规划**：管理员修改人数、预算或替代食材时，只重算受影响节点，不重新开启无关流程。
5. **人工确认**：预览、比较和解释可由 Agent 完成；保存、发布、库存扣减等副作用必须由管理员明确确认。
6. **反馈闭环**：规划前读取上一餐评分、快捷标签、备注和剩余等级，形成下一次排序特征与改进理由。
7. **可观测与降级**：显示工具、输入摘要、耗时和结果；LLM 超时后仍能返回规则基线方案。

## 4. LangGraph 状态与节点

```text
START
  → parse_request
  → validate_context ──缺字段→ ask_clarification
  → load_context（餐次/库存/反馈）
  → retrieve_candidates
  → hard_filter
  → build_options（临期/成本/满意度）
  → calculate_quantity_cost_nutrition
  → risk_review
  → explain_options
  → wait_for_human
      ├─ revise → apply_changes → risk_review
      └─ approve → publish_menu → END
```

状态至少包含 `workspace_id`、`site_id`、`meal_service_id`、`request_text`、`constraints`、`inventory_snapshot`、`feedback_summary`、`candidate_recipes`、`menu_options`、`selected_option`、`tool_trace`、`warnings` 和 `approval_status`。

## 5. 工具白名单

| 工具 | 类型 | 作用 |
| --- | --- | --- |
| `get_meal_service_context` | 只读 | 读取站点、餐次和预计人数。 |
| `list_inventory` | 只读 | 返回可用、临期和过期库存。 |
| `get_feedback_summary` | 只读 | 汇总历史评分、标签、备注与剩余等级。 |
| `search_recipe_candidates` | 只读 | 从结构化菜谱库召回候选。 |
| `filter_hard_constraints` | 确定性计算 | 过滤过敏原、禁用食材、时长和厨具冲突。 |
| `scale_recipe_quantities` | 确定性计算 | 按预计人数换算用量。 |
| `score_menu_options` | 确定性计算 | 按临期、成本、满意度等评分。 |
| `estimate_nutrition_and_cost` | 确定性计算 | 返回人均热量估算与成本。 |
| `build_procurement_list` | 确定性计算 | 计算菜单所需量减库存后的采购缺口。 |
| `publish_meal_plan` | 写操作 | 仅在管理员确认后发布。 |

## 6. 多方案与反馈策略

三种方案使用相同硬约束，只调整软目标权重。匿名反馈不直接改变过敏原等硬规则；低样本量时只作为解释信息。MVP 可采用可配置加权分数，后续积累数据后再训练接受率或剩余风险模型。

## 7. Agent 证据与反模式

现场至少应看到：结构化约束、缺字段追问或校验、五个以上真实工具节点、三方案取舍、一次基于当前状态的重规划、一次人工确认、一次反馈驱动调整和一次模型故障降级。

以下实现不能作为 Agent 亮点：

- 把预先写死的菜单包装成模型实时生成结果。
- 只做一次 Prompt → 文本回答，没有工具调用和状态。
- 由模型直接编写成本、库存和热量数字。
- 每次修改人数都重新开始，无法引用当前方案。
- Agent 未经确认直接发布菜单或扣减库存。
- 只展示“正在思考”动画，却没有可验证的工具结果。

## 8. 评测

固定测试集至少覆盖：正常生成、缺人数追问、过敏原冲突、库存不足、预算降低、人数从 120 增至 150、匿名反馈回流、工具失败、模型超时降级、管理员拒绝发布。指标包括约束抽取正确率、硬约束通过率、采购计算准确率、工具调用成功率、平均规划时长和降级成功率。
