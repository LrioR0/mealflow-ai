# MealFlow V1 演示脚本（5–7 分钟）

> 演示目标：证明这是一个能完成多步业务决策的 Agent，而不是带聊天框的食堂管理系统。至少 70% 演示时间用于 Agent，库存与采购页面只用于验证事实来源和执行结果。

## 开场（30 秒）

建议话术：

> 传统食堂系统能记录库存、菜单和采购，但“明天做什么、为什么这样做、条件变化后怎么调整”仍主要依靠管理员人工判断。MealFlow 让 Agent 理解运营目标、主动读取业务数据、调用计算工具并比较方案，同时把发布权保留给人。

## 主流程

1. **痛点与任务，30 秒**：直接展示预置的明日午餐 120 人、预算 900 元、花生限制和两天内到期的番茄，不在现场手工录入。
2. **目标理解，40 秒**：输入“明天午餐 120 人，预算 900 元，清淡，优先消耗临期番茄，不能含花生”。展示 Agent 提取的结构化约束；可用一个缺预算的短输入补充演示追问能力。
3. **自主执行，70 秒**：展示 Agent 依次读取餐次、库存和反馈，检索菜谱，执行硬过滤、人数换算、成本/热量和采购缺口。每个节点显示真实状态、耗时和结果摘要。
4. **决策取舍，60 秒**：比较临期优先、成本优先、满意度优先三个方案。重点讲“没有唯一最优解”，以及 Agent 如何解释成本、浪费、满意度和风险之间的权衡。
5. **有状态重规划，60 秒**：在当前 Agent Run 中把人数改为 150，再把预算降低 200 元。突出受影响节点重新执行，批量用量、成本和采购缺口同步变化，而不是重新生成一段无关文本。
6. **可信执行与人机协同，40 秒**：点击菜品验证批量原料和热量来源；展示花生硬过滤；管理员确认前发布按钮不可执行，确认后才发布。
7. **反馈闭环，50 秒**：在 `/kiosk` 连续提交“满意 + 份量少”和“太咸 + 备注”，证明自动重置；下一轮 Agent 引用聚合摘要并解释方案变化。
8. **企业级保障，30 秒**：开启故障开关模拟模型超时，展示规则基线继续执行硬过滤、人数换算和采购计算。

## 必须让观众看到的证据

- 结构化约束卡片，而不只是聊天气泡。
- Agent 节点/工具时间线，至少五个真实节点。
- 三方案并排对比及评分拆解。
- What-if 前后差异高亮。
- `WAITING_APPROVAL` 与确认发布状态变化。
- 反馈摘要如何影响下一轮的说明。
- `FALLBACK` 降级标识与仍然正确的计算结果。

## 收尾话术

> MealFlow 不是替代管理员做最终决定，而是把分散在库存、菜谱、人数、预算和反馈中的信息编排成可解释的方案。它区别于传统 CRUD 系统的核心，是能根据自然语言目标自主调用工具、随条件变化重规划，并通过反馈持续改进；区别于普通大模型聊天框的核心，是数据有来源、计算可验证、操作需审批、失败可降级。

## 演示准备

- 使用固定种子数据并准备一键重置。
- 演示前 24 小时冻结千问主模型、接口地址和提示词模板，并验证 DeepSeek 备用配置；智谱只在提前通过固定用例后替换。
- 云端模型不可控时先切备用 Provider，再进入规则降级；不要把缓存或写死回答伪装成实时 Agent 结果。
- 演示前连续完整运行两遍，关闭无关通知和开发工具窗口。
- 不使用真实政府单位名称、人员信息或生产数据。
